# ActShift 要件定義書 v1.0

- 作成日： 2026年10月13日
- 対象OS： Windows / macOS
- 開発形態： クロスプラットフォーム・デスクトップアプリ
- 初期利用対象： 個人利用
- 文書ステータス： 要件統合版・技術検証および一部仕様の確定前
- アプリ名： ActShift

## 概要

これまでの検討内容を統合し、<strong>要件定義書 v1.0（設計基準案）</strong>として整理します。
今回の最も重要な変更点は、アプリの目的を「SNSを制限すること」から、<strong>「自分にとって無益だと感じる行動を、有益だと感じる行動へ転換すること」</strong>へ再定義した点です。
これにより、SNSブロック、厳格ロック、遅延一時解除、行動誘発、曜日別ルーティンを、単一の目的に従う機能群として構成します。

## プロダクトの基本思想

無益な行動を、自分にとって有益な行動へ。
SNSに費やしていた時間を、本人が望む学習・読書・運動・創作・休息などへ転換する。そのために、環境的な制限と、行動を始めやすくする支援を組み合わせる。

## 第1章　プロダクト概要

### 1.1 プロダクトの思想

本アプリの根本的な思想は、<strong>「無益な行動を、自分にとって有益な行動へ転換するシステムを作ること」</strong>である。
SNSや動画サービスの利用を単純に禁止するのではなく、ユーザーが望まないまま繰り返す行動を抑制し、自分の価値観や目標に合った行動へ移行できる環境を構築する。
何が無益で何が有益かは、アプリが一律に判断しない。ユーザー自身が定義し、利用状況や経験を踏まえて変更できるものとする。

### 1.2 解決したい課題

SNSや動画サービスの利用に関して、以下の課題を想定する。
1. 意図せずSNSを開き、予定以上に時間を費やす。
2. 閲覧終了後に無気力感や疲労感を覚え、本来の活動を始めにくくなる。
3. 利用制限を設定しても、自分で容易に解除してしまう。
4. SNSを制限できても、代わりに何をするか決められない。
5. 学習、読書、運動などを習慣化したくても、開始するきっかけが不足する。
6. 時間帯や本人の状態によって、適切な行動が異なる。

なお、SNS利用後の無気力感をドーパミンの減少や異常のみで説明することはできない。本アプリは医学的な治療ではなく、利用者の行動と環境を調整するための支援システムとする。

### 1.3 プロダクトの提供価値

本アプリは、次の4段階で行動転換を支援する。
制限 → 行動誘発 → 習慣実行 → 振り返り
- 制限：意図しないSNS利用を環境的に抑える。
- 行動誘発：ユーザーに適した行動の開始を促す。
- 習慣実行：曜日・時間帯別のルーティンを実践する。
- 振り返り：行動転換に有効だった条件を把握する。

### 1.4 設計原則

原則A：禁止は目的ではなく手段とする。
SNSを使わなかった時間だけでなく、その時間を本人がどう活用できたかを重視する。
原則B：制限は強く、活動支援は柔軟にする。
SNSの厳格ロックを維持しながら、習慣や行動誘発タスクの未達成に罰則を設けない。
原則C：行動開始の認知的負担を減らす。
「勉強する」など抽象的な指示ではなく、「参考書を開く」など具体的な最初の行動を提示する。
原則D：個人にとって効果のある行動を尊重する。
外出、散歩、読書などを個人の活動トリガーとして登録できる。
原則E：安全性と復旧可能性を維持する。
強固な制限を実装する場合でも、端末の管理機能や緊急時の復旧経路を破壊しない。

## 第2章　対象ユーザーと利用環境

### 2.1 対象ユーザー

初期MVPでは個人利用を対象とする。
想定する利用者は、SNSや動画サイトの利用を自ら制限し、学習・仕事・読書・運動・創作などの行動を習慣化したい人である。
将来的な一般公開や課金機能は未確定とする。

### 2.2 対応プラットフォーム

- Windowsデスクトップ
- macOSデスクトップ

両OSで共通の設定UI、習慣管理、ルールエンジンを提供する。
OSレベルの通信遮断やプロセス制御については、Windows・macOS固有の実装を許容する。

### 2.3 対象サービス

<strong>初期プリセット候補：</strong>
- YouTube
- Twitch
- X
- Instagram
- Reddit
- Discord

これらは初期登録の候補であり、すべてが初期状態から制限有効になるとは限らない。
ユーザーは対象ドメインやネイティブアプリを自由に追加・変更できる。

## 第3章　機能要件

### FR-01　Webサイト制限

優先度：MVP必須
ユーザーが登録したWebサイトへのアクセスを、指定された条件に従ってブロックする。

<strong>要求事項：</strong>
- Safari、Chrome、Firefox、Edgeなどを対象とする。
- ブラウザ拡張機能を必要としない。
- OSレベルの通信制御を利用する。
- サービス単位で関連ドメインを管理する。
- 対象サイトの追加・削除・編集を可能にする。
- 制限中の新規アクセスおよび既存通信を遮断する。

対象ドメインの一部がCDNや他サービスと共有されることを考慮し、過剰遮断を検証する。
暗号化DNS、VPN、QUIC、IPv6などの通信経路も検証対象とする。

### FR-02　ネイティブアプリ制限

優先度：MVP必須
Discordなど、ブラウザを介さず実行されるネイティブアプリを制限する。

<strong>要求事項：</strong>
- 対象アプリを登録できる。
- アプリ単位で通信を遮断できる。
- OS側のプロセス・アプリ識別情報を利用する。
- ブラウザ版とネイティブ版を同じ制限グループに登録できる。

対象ネイティブアプリはネットワーク通信のみを遮断し、起動自体は禁止しない。MVPではネットワーク機能を実効的に遮断する。

### FR-03　時間帯・曜日別制限

優先度：MVP必須
曜日・開始時刻・終了時刻を指定して制限する。

<strong>設定例：</strong>
- 月〜金：9:00〜15:00はSNS禁止
- 土曜日：10:00〜12:00はSNS禁止
- 日曜日：制限なし

<strong>要求事項：</strong>
- 複数の時間帯ルールを登録できる。
- 曜日ごとに異なるルールを設定できる。
- 制限対象グループごとにスケジュールを持てる。
- 日付変更や日をまたぐ時間帯に対応する。
- 設定済みのルールを週単位で繰り返す。

### FR-04　周期制限

優先度：MVP必須
利用可能時間とブロック時間を交互に切り替える。

<strong>例：</strong>
利用30分 → ブロック30分 → 利用30分 → ブロック30分

<strong>要求事項：</strong>
- 利用可能時間N分を設定できる。
- ブロック時間M分を設定できる。
- NとMは独立して設定できる。
- 同じグループ内では共通のタイマーを使用する。
- ブラウザや対象サイトを切り替えても、タイマーをリセットしない。
- アクセス可能時間として計測し、途中でサイトを閉じても時間を停止しない。

### FR-05　初回アクセスを起点とした周期開始

優先度：MVP必須
対象サイトまたはネイティブアプリへの最初のアクセスを検知して周期を開始する。
状態遷移：
IDLE → ALLOW → BLOCK → ALLOW → BLOCK…

<strong>要求事項：</strong>
- IDLE中は周期タイマーを進めない。
- 対象への最初のアクセスでALLOWを開始する。
- 同一グループ内での複数アクセスはタイマーを重複開始しない。
- 開始後の周期は、対象サイトの閲覧を終了しても継続する。
- 再起動・スリープから復帰した場合も、保存された時刻から状態を再計算する。
- 毎朝10:00に、進行中のALLOW/BLOCKを含め周期をIDLEへ戻す。次の対象アクセスを新たな初回アクセスとしてALLOWを開始する。他の時間帯・ルーティン制限や厳格ロックは解除しない。

初回アクセスの検知方式はOSごとに技術検証を要する。

### FR-06　厳格ロック

優先度：MVP必須
制限中の安易な設定変更や通常解除を禁止する。

<strong>要求事項：</strong>
- 厳格ロックを基本モードとして採用する。
- 制限対象の削除による回避を防止する。
- 厳格ロックの設定期間は30分以上とする。
- 厳格ロック中は、制限を緩める変更・厳しくする変更を含め、通常の設定変更を一律に禁止する。
- 厳格ロック中以外も、21:00〜翌10:00は通常の設定編集を禁止し、10:00〜21:00に可能とする。
- UIを終了しても制限を継続する。
- OSの再起動後も制限状態を復元する。
- 通常ユーザーが制御サービスを容易に変更できない権限構成を採用する。
- 正規の管理者・緊急復旧経路を確保する。

端末の完全な管理者権限を持つ本人に対して、解除不可能であることまでは保証しない。

### FR-07　遅延一時解除

優先度：MVP必須
厳格ロックに付随する独立した例外機能とする。

<strong>設定例：</strong>
- 解除待機時間：20分
- 解除後の利用可能時間：20分

<strong>動作：</strong>
1. ユーザーが一時解除を要求する。
2. 20分間、制限を維持する。
3. 待機終了後、本人の再確認を受けて20分間の一時許可を開始する。
4. 一時許可終了時に自動的に再ロックする。

<strong>要求事項：</strong>
- 待機時間を設定できる。
- 一時許可時間は待機時間と同じ長さとする。
- 待機中の再要求で時間を短縮しない。
- 待機中に解除要求を取り消せる。
- PC再起動による待機時間のリセットを防ぐ。
- 一時解除は恒久的なロック設定を変更しない。
- 解除要求や一時許可の履歴を保存する。
- 一時解除は時間帯制限およびルーティン連動制限を上書きしない。

一時解除を周期制限以外のどの制限に適用するかは、詳細設計で明確化する。

### FR-08　個人別の活動トリガー登録

優先度：MVP必須
活動を開始しやすくする個人的な行動を登録する。

<strong>例：</strong>
- 外に出る。
- 5分間散歩する。
- 本を机に置く。
- 水を飲む。
- IDEを開く。
- 部屋を片付ける。

<strong>要求事項：</strong>
- 行動名を自由に登録できる。
- 行動をカテゴリ別に分類できる。
- 最初の具体的な行動を設定できる。
- 実施に適した時間帯を指定できる。
- 活動エネルギーに応じた代替行動を登録できる。
- 他の習慣を開始するための前提行動として指定できる。

初期利用者向けには「外出」を優先的な活動トリガーとして設定する。

### FR-09　時間帯別の行動誘発

優先度：MVP必須
SNSのブロック中、現在時刻に適した活動を提示する。
時間帯の初期例：
- 6:00〜9:00：朝の活動開始
- 9:00〜15:00：短い休憩・作業復帰
- 15:00〜18:00：外出・散歩・学習
- 18:00〜21:00：読書・片付け・生活習慣
- 21:00〜6:00：休息・翌日の準備

<strong>要求事項：</strong>
- 時間帯別のタスクテンプレートを設定できる。
- ユーザーが時間帯と行動を編集できる。
- 活動状態に応じて軽い代替タスクを提示できる。
- 夜間や体調不良時に無理な外出を強制しない。
- 同じタスクの過剰な繰り返し通知を防止する。

### FR-10　段階的行動誘導

優先度：MVP必須
抽象的な活動を小さな行動へ分解し、順番に提示する。

<strong>例：</strong>
「数学を勉強する」
1. 椅子に座る。
2. 参考書を開く。
3. 前回の学習箇所を確認する。
4. 最初の問題に取り組む。

<strong>要求事項：</strong>
- タスクを複数のステップに分けられる。
- ステップごとに進捗を記録できる。
- タスクを途中終了できる。
- 活動誘導のみを一時停止できる。
- 誘導の一時停止によってSNSの厳格ロックを解除しない。

### FR-11　曜日別ルーティン管理

優先度：MVP必須
勉強、読書、運動、開発などを習慣として登録し、曜日ごとに予定を作成する。

<strong>要求事項：</strong>
- 習慣の作成・編集・削除。
- 実施曜日の設定。
- 開始・終了時刻の設定。
- 目標所要時間の設定。
- 最低達成時間の設定。
- 開始前通知の設定。
- 開始トリガーの設定。
- 毎週の繰り返し設定。
- 週間カレンダー表示。
- ルーティンの実行履歴保存。

同じ習慣を複数の曜日・時間帯に登録できる。複数のルーティンが重複した場合は後から登録したものを優先し、先に登録したものをサブルーティンとして扱う。繰り延べやスキップの場合は、休息または読書・瞑想などの低刺激タスクを提示する。実行できなかったことを責めない。

### FR-12　ルーティンとSNSブロックの連携

優先度：MVP必須
ルーティン実行中にSNSの利用制限を適用できる。

<strong>要求事項：</strong>
- ルーティンにSNS制限の有効・無効を設定できる。
- SNS制限中でもルーティンを開始できる。
- 予定された習慣を行動誘発タスクより優先表示できる。
- ルーティン未達成に対する罰則を設けない。
- ルーティン終了だけを条件に厳格ロックを解除しない。

### FR-13　通知・行動誘導UI

優先度：MVP必須
通知を見逃しにくくし、次に行う行動を明確に提示する。

<strong>要求事項：</strong>
- デスクトップ通知。
- 通知音の設定。
- 前面表示による行動誘導。
- SNSのブロック開始5分前の通知、およびブロック開始通知。
- 習慣開始前の予告通知。
- 行動ステップの表示。
- 通知の一時停止。停止時間は15分以上で設定できる。
- 前面表示と繰り返し通知の頻度に設定上の上限は設けない。
- 安全上必要な操作や通常業務を妨害しない表示方法。

### FR-14　活動記録

優先度：MVP必須
習慣や誘発された行動の実行結果を保存する。

<strong>記録項目：</strong>
- 対象習慣。
- 実行日時。
- 実行時間。
- 完了・一部実行・未実行。
- 行動開始に成功したか。
- 任意のメモ。

本人が実行できなかった理由を入力することは任意とする。

### FR-15　利用前後の状態記録

優先度：後続機能
SNS利用前後の活動意欲や疲労感を記録する。

<strong>取得候補：</strong>
- 利用前の活動意欲。
- 利用後の活動意欲。
- 主観的な疲労感。
- 次の活動に移るまでの時間。

記録頻度を過度に高くしない。

### FR-16　行動転換の分析

優先度：後続機能
記録された行動データを分析し、活動転換に有効な条件を可視化する。

<strong>分析候補：</strong>
- SNS利用時間。
- 習慣実行率。
- 行動開始率。
- 外出後の活動復帰率。
- 時間帯別の活動成功率。
- 行動誘発タスク別の結果。

将来的には本人の実績に応じた行動推薦の最適化を検討する。

## 第4章　ユーザーフロー

### 4.1 SNSアクセス時

1. ユーザーが対象サービスにアクセスする。
2. OSレベルでアクセスを検知する。
3. 現在の制限ルールを評価する。
4. アクセス可能な場合、初回アクセスを起点にタイマーを開始する。
5. 利用可能時間を超えた場合、対象サービスを遮断する。
6. 行動誘発エンジンが適切なタスクを提示する。
7. タスク実行結果を保存する。

### 4.2 週間ルーティン実行時

1. 設定された曜日・時刻が近づく。
2. 予告通知を表示する。
3. 開始トリガーを提示する。
4. ルーティン開始画面を表示する。
5. 実行中は必要に応じてSNS制限を適用する。
6. 目標時間の終了後、実行結果を記録する。

### 4.3 遅延一時解除時

1. 厳格ロック中に解除を要求する。
2. 待機状態へ移行する。
3. 規定の待機時間が経過する。
4. 本人が再確認した後、一時的に対象サービスを許可する。
5. 許可時間終了後に自動再ロックする。
6. 一時解除履歴を保存する。

## 第6章　制御ルールと優先順位

### 6.1 SNSアクセス判定

アクセス許可・遮断は以下を踏まえて決定する。
1. OS側の安全・復旧要件。
2. 厳格ロックの有効性。
3. 有効な遅延一時解除。
4. 時間帯制限。
5. ルーティン連動制限。
6. 周期制限。

複数の制限が有効な場合、原則として制限の厳しい判定を優先する。
一時解除は時間帯制限とルーティン連動制限を上書きしない。その他の適用範囲は詳細設計で明確化する。

### 6.2 行動誘発の優先順位

1. 安全性・体調・必要な休息。
2. 実行中の習慣。
3. 開始予定の習慣。
4. SNSブロックに伴う行動誘発。
5. 空き時間に行う任意の活動。

### 6.3 時間管理

- 時刻はOSの時計とタイムゾーンを考慮して扱う。
- 再起動後に状態を復元する。
- 時計を手動変更した場合の不正な短縮を検知する。
- スリープ中の経過時間を含めるかは、ルールごとに明確化する。
- 異常終了時は状態記録から再計算する。

## 第7章　非機能要件

### NFR-01　セキュリティ

- 設定UIと制御サービスを分離する。
- 制御サービスには必要最小限の権限を与える。
- 権限のない設定変更を拒否する。
- 正規の復旧経路を維持する。
- 機密性の高い閲覧内容を不要に収集しない。

### NFR-02　信頼性

- UIの終了によって遮断機能が停止しない。
- 再起動後も設定を維持する。
- 設定の破損を検知する。
- ロック状態の不整合を検出・記録する。
- OSのネットワーク機能を恒久的に破壊しない。
- 制御機能の停止・異常終了時は登録済み対象サービスのみ遮断し、それ以外の通信は許可する。制御サービスの自動再起動を試み、異常を記録・表示し、正規の管理者復旧経路を維持する。

### NFR-03　性能

- 常駐状態でのCPU・メモリ負荷を低く保つ。
- 通常のインターネット通信に不要な遅延を生じさせない。
- タスク通知とルーティン判定を安定して実行する。

具体的な性能上限値は技術検証時に設定する。

### NFR-04　プライバシー

- 個人用MVPではローカル保存を基本とする。
- クラウドアカウントを必須としない。
- 行動履歴や習慣データを外部送信しない。
- 記録データの削除・エクスポートを可能にする。

### NFR-05　ユーザビリティ

- 現在のロック状態を明確に表示する。
- 行動開始に必要な操作を少なくする。
- 通知音を設定できる。
- 未達成を責める表現を使わない。
- 行動誘発の介入強度を変更できる。

### 11.3 行動誘発

## 第12章　決定事項と詳細設計での確認事項

### U-01：ネイティブアプリの制限範囲【決定】

ネットワーク通信のみを遮断し、起動自体は禁止しない。

### U-02：周期の終了条件【決定】

毎朝10:00に、進行中のALLOW/BLOCKを含め周期をIDLEへ戻す。次の対象アクセスを新たな初回アクセスとする。他の時間帯・ルーティン制限や厳格ロックは解除しない。

### U-03：一時解除の適用範囲【一部決定】

時間帯制限とルーティン連動制限は一時解除で上書きできない。その他の適用範囲は詳細設計で明確化する。

### U-04：待機完了時の挙動【決定】

待機終了後、本人の再確認を受けて一時許可を開始する。再確認までは制限を維持する。

### U-05：タスク通知の強度【一部決定】

制限開始5分前に通知する。前面表示と繰り返しの頻度に上限は設けない。通知の一時停止時間は15分以上で設定可能とする。通知の発火条件と、同一タスクの過剰通知を防ぐ方法は詳細設計で整合を取る。

### U-06：厳格ロックの期限と編集【決定】

厳格ロックの設定期間は30分以上。ロック中は、制限を厳しくする変更を含め通常の設定編集を一律に禁止する。ロック中以外も21:00〜翌10:00は通常編集を禁止し、10:00〜21:00を編集可能時間とする。正規の管理者・緊急復旧経路は維持する。

### U-07：失敗時の通信制御【方針決定・技術検証待ち】

制御機能の停止・異常終了時は登録済み対象サービスのみ遮断し、それ以外の通信は許可する。制御サービスの自動再起動を試み、異常を記録・表示し、正規の管理者復旧経路を維持する。Windows・macOSでこの動作を保証できるか検証する。対象を識別できない場合の扱いも詳細設計で定める。

### U-08：予定の競合処理【方針決定】

重複時は後から登録したルーティンを優先し、先に登録したものをサブルーティンとする。繰り延べやスキップ時には休息、読書、瞑想などの低刺激タスクを提示する。実行できなくても罪悪感を強めない表現とする。サブルーティンの実行・記録方法は詳細設計で定める。

### U-09：習慣化の評価基準【方針決定】

SNSを見ていたはずの時間を本人がどう過ごせたかを重視する。ルーティン未達成でも、SNSを見ず穏やかに過ごせたことを肯定的な結果として扱う。行動開始や本人の自己評価も用い、単一の達成率で本人の価値を判定しない。測定方法は詳細設計で定める。

## 第13章　成功指標

本アプリの成功を、SNSを何時間ブロックできたかだけでは判断しない。
最上位の成果指標は、<strong>「本人が有益だと定義した行動へ移行できたか」</strong>とする。

<strong>主要指標：</strong>
- SNSの意図しない利用時間。
- 行動誘発後の着手率。
- 習慣の実行率。
- 習慣を開始するまでの時間。
- 行動転換の自己評価。

<strong>補助指標：</strong>
- 遅延解除要求の回数と取り消し率。
- ルーティンの継続率。
- タスク通知の無視率。
- SNS利用後の主観的疲労・活動意欲。

これらを利用者の能力や価値の評価に使用せず、アプリの介入が有効かどうかの判断材料とする。

## 第14章　開発着手基準

本書の機能要件を実現するには、OSレベルの通信遮断と初回アクセス検知が最大の技術的課題となる。
本格的なUI実装より前に、Windows・macOSでそれぞれ以下を実証する。
1. ブラウザ拡張に依存しない対象サイト遮断。
2. 対象サービスへの初回アクセス検知。
3. ネイティブアプリの通信遮断。
4. ブロック中の既存通信への適用。
5. サービス終了・OS再起動時の制限維持。
6. 厳格ロックと安全な復旧の両立。

これらの技術検証と未確定事項の解消をもって、詳細設計および実装計画の確定へ進む。

## 最終定義

本アプリは、ユーザー自身が無益だと感じる行動を環境的に抑制し、その時間を本人が有益だと定義した行動に転換できるよう支援する、Windows・macOS対応の行動制御・習慣形成システムである。
SNSブロックは行動を止める手段、習慣管理は行動を継続する仕組み、行動誘発エンジンはその両者をつなぐ機能として位置づける。
