# ActShift 要件定義書 v1.0

- 作成日： 2026年10月13日
- 対象OS： Windows / macOS
- 開発形態： クロスプラットフォーム・デスクトップアプリ
- 初期利用対象： 個人利用
- 文書ステータス： 要件統合版・技術検証および一部仕様の確定前
- アプリ名： ActShift

## 概要

これまでの検討内容を統合し、<strong>要件定義書 v1.0（設計基準案）</strong>として整理します。
今回の最も重要な変更点は、アプリの目的を「SNSを制限すること」から、<strong>「自分にとって無益だと感じる行動を、有益だと感じる行動へ転換すること」</strong>へ再定義した点です。
これにより、SNSブロック、厳格ロック、行動誘発、曜日別ルーティンを、単一の目的に従う機能群として構成します。

## プロダクトの基本思想

無益な行動を、自分にとって有益な行動へ。
SNSに費やしていた時間を、本人が望む学習・読書・運動・創作・休息などへ転換する。そのために、環境的な制限と、行動を始めやすくする支援を組み合わせる。

## 第1章　プロダクト概要

### 1.1 プロダクトの思想

本アプリの根本的な思想は、<strong>「無益な行動を、自分にとって有益な行動へ転換するシステムを作ること」</strong>である。
SNSや動画サービスの利用を単純に禁止するのではなく、ユーザーが望まないまま繰り返す行動を抑制し、自分の価値観や目標に合った行動へ移行できる環境を構築する。
何が無益で何が有益かは、アプリが一律に判断しない。ユーザー自身が定義し、利用状況や経験を踏まえて変更できるものとする。

### 1.2 解決したい課題

SNSや動画サービスの利用に関して、以下の課題を想定する。
1. 意図せずSNSを開き、予定以上に時間を費やす。
2. 閲覧終了後に無気力感や疲労感を覚え、本来の活動を始めにくくなる。
3. 利用制限を設定しても、自分で容易に解除してしまう。
4. SNSを制限できても、代わりに何をするか決められない。
5. 学習、読書、運動などを習慣化したくても、開始するきっかけが不足する。
6. 時間帯や本人の状態によって、適切な行動が異なる。

なお、SNS利用後の無気力感をドーパミンの減少や異常のみで説明することはできない。本アプリは医学的な治療ではなく、利用者の行動と環境を調整するための支援システムとする。

### 1.3 プロダクトの提供価値

本アプリは、次の4段階で行動転換を支援する。
制限 → 行動誘発 → 習慣実行 → 振り返り
- 制限：意図しないSNS利用を環境的に抑える。
- 行動誘発：ユーザーに適した行動の開始を促す。
- 習慣実行：曜日・時間帯別のルーティンを実践する。
- 振り返り：行動転換に有効だった条件を把握する。

### 1.4 設計原則

原則A：禁止は目的ではなく手段とする。
SNSを使わなかった時間だけでなく、その時間を本人がどう活用できたかを重視する。
原則B：制限は強く、活動支援は柔軟にする。
SNSの厳格ロックを維持しながら、習慣や行動誘発タスクの未達成に罰則を設けない。
原則C：行動開始の認知的負担を減らす。
「勉強する」など抽象的な指示ではなく、「参考書を開く」など具体的な最初の行動を提示する。
原則D：個人にとって効果のある行動を尊重する。
外出、散歩、読書などを個人の活動トリガーとして登録できる。
原則E：安全性と復旧可能性を維持する。
強固な制限を実装する場合でも、端末の管理機能や緊急時の復旧経路を破壊しない。

## 第2章　対象ユーザーと利用環境

### 2.1 対象ユーザー

初期MVPでは個人利用を対象とする。
想定する利用者は、SNSや動画サイトの利用を自ら制限し、学習・仕事・読書・運動・創作などの行動を習慣化したい人である。
将来的な一般公開や課金機能は未確定とする。

### 2.2 対応プラットフォーム

- Windowsデスクトップ
- macOSデスクトップ

両OSで共通の設定UI、習慣管理、ルールエンジンを提供する。
OSレベルの通信遮断やプロセス制御については、Windows・macOS固有の実装を許容する。

### 2.3 対象サービス

<strong>初期状態で制限を有効にするサービス：</strong>
- YouTube
- Twitch
- X
- ユーザーローカル ライブランキング（https://live-ranking.userlocal.jp/）
- 好き嫌い.com（https://suki-kira.com/）
- Yahoo!ファイナンス（https://finance.yahoo.co.jp/）

Instagram、Reddit、Discordなどは追加登録可能な対象例とし、初期状態では制限を有効にしない。
ユーザーは対象ドメインやネイティブアプリを自由に追加・変更できる。

## 第3章　機能要件

### FR-01　Webサイト制限

優先度：MVP必須
ユーザーが登録したWebサイトへのアクセスを、指定された条件に従ってブロックする。

<strong>要求事項：</strong>
- Safari、Chrome、Firefox、Edgeなどを対象とする。
- ブラウザ拡張機能を必要としない。
- OSレベルの通信制御を利用する。
- サービス単位で関連ドメインを管理する。
- 対象サイトの追加・削除・編集を可能にする。
- 制限中の新規アクセスおよび既存通信を遮断する。

対象ドメインの一部がCDNや他サービスと共有されることを考慮し、過剰遮断を検証する。
暗号化DNS、VPN、QUIC、IPv6などの通信経路も検証対象とする。

### FR-02　ネイティブアプリ制限

優先度：MVP必須
Discordなど、ブラウザを介さず実行されるネイティブアプリを制限する。

<strong>要求事項：</strong>
- 対象アプリを登録できる。
- アプリ単位で通信を遮断できる。
- OS側のプロセス・アプリ識別情報を利用する。
- ブラウザ版とネイティブ版を同じ制限グループに登録できる。

対象ネイティブアプリはネットワーク通信のみを遮断し、起動自体は禁止しない。ブラウザ版と同じ制限グループに登録した場合は同じ周期タイマーを使う。MVPではネットワーク機能を実効的に遮断する。

### FR-03　時間帯・曜日別制限

優先度：MVP必須
曜日・開始時刻・終了時刻を指定して制限する。

<strong>設定例：</strong>
- 月〜金：9:00〜15:00はSNS禁止
- 土曜日：10:00〜12:00はSNS禁止
- 日曜日：制限なし

<strong>要求事項：</strong>
- 複数の時間帯ルールを登録できる。
- 曜日ごとに異なるルールを設定できる。
- 制限対象グループごとにスケジュールを持てる。
- 日付変更や日をまたぐ時間帯に対応する。日をまたぐ予定は開始日の曜日に属するものとして扱う。
- 設定済みのルールを週単位で繰り返す。

### FR-04　周期制限

優先度：MVP必須
利用可能時間とブロック時間を交互に切り替える。

<strong>例：</strong>
利用30分 → ブロック30分 → 利用30分 → ブロック30分

<strong>要求事項：</strong>
- 利用可能時間N分は5〜30分の範囲で設定できる。
- ブロック時間M分は30〜500分の範囲で設定できる。
- NとMは独立して設定できる。
- 同じグループ内では共通のタイマーを使用する。
- ブラウザや対象サイトを切り替えても、タイマーをリセットしない。
- アクセス可能時間として計測し、途中でサイトを閉じても時間を停止しない。

### FR-05　初回アクセスを起点とした周期開始

優先度：MVP必須
対象サイトまたはネイティブアプリへの最初のアクセスを検知して周期を開始する。
状態遷移：
IDLE → ALLOW → BLOCK → ALLOW → BLOCK…

<strong>要求事項：</strong>
- IDLE中は周期タイマーを進めない。
- 対象への最初のアクセスでALLOWを開始する。
- 同一グループ内での複数アクセスはタイマーを重複開始しない。
- 開始後の周期は、対象サイトの閲覧を終了しても継続する。
- 再起動・スリープから復帰した場合も、保存された時刻から状態を再計算する。
- 毎朝10:00に、進行中のALLOW/BLOCKを含め周期をIDLEへ戻す。対象サイトを開いたまま、または対象ネイティブアプリを起動したままの場合も10:00に新しいALLOWを開始する。対象を閉じている場合は次の対象アクセスでALLOWを開始する。他の時間帯・ルーティン制限や厳格ロックは解除しない。

初回アクセスの検知方式はOSごとに技術検証を要する。

### FR-06　厳格ロック

優先度：MVP必須
制限中の安易な設定変更や通常解除を禁止する。

<strong>要求事項：</strong>
- 厳格ロックを基本モードとして採用する。
- 制限対象の削除による回避を防止する。
- 厳格ロックの設定期間は30分以上とする。
- 厳格ロック中は、制限を緩める変更・厳しくする変更を含め、通常の設定変更を一律に禁止する。
- 厳格ロック中以外も、21:00〜翌10:00は通常の設定編集と保存を禁止し、10:00〜21:00に可能とする。21:00時点で編集中の未保存変更は適用せず下書きとして保持し、翌10:00以降、厳格ロックが無効であれば保存できる。
- UIを終了しても制限を継続する。
- OSの再起動後も制限状態を復元する。
- 通常ユーザーが制御サービスを容易に変更できない権限構成を採用する。
- 正規の管理者・緊急復旧経路を確保する。

端末の完全な管理者権限を持つ本人に対して、解除不可能であることまでは保証しない。

### FR-07　一時解除なし

優先度：MVP必須
通常の設定画面から制限を一時解除する機能は設けない。周期制限・時間帯制限・ルーティン連動制限・厳格ロックのいずれも、一時解除で上書きできない。正規の管理者・緊急復旧経路は維持する。

### FR-08　個人別の活動トリガー登録

優先度：MVP必須
活動を開始しやすくする個人的な行動を登録する。

<strong>例：</strong>
- 外に出る。
- 5分間散歩する。
- 本を机に置く。
- 水を飲む。
- IDEを開く。
- 部屋を片付ける。

<strong>要求事項：</strong>
- 行動名を自由に登録できる。
- 行動をカテゴリ別に分類できる。
- 最初の具体的な行動を設定できる。
- 実施に適した時間帯を指定できる。
- 活動エネルギーに応じた代替行動を登録できる。
- 他の習慣を開始するための前提行動として指定できる。

初期利用者向けには「外出」を優先的な活動トリガーとして設定する。

### FR-09　時間帯別の行動誘発

優先度：MVP必須
SNSのブロック中、現在時刻に適した活動を提示する。
時間帯の初期例：
- 6:00〜9:00：朝の活動開始
- 9:00〜15:00：短い休憩・作業復帰
- 15:00〜18:00：外出・散歩・学習
- 18:00〜21:00：読書・片付け・生活習慣
- 21:00〜6:00：休息・翌日の準備

<strong>要求事項：</strong>
- 時間帯別のタスクテンプレートを設定できる。
- ユーザーが時間帯と行動を編集できる。
- 活動状態に応じて軽い代替タスクを提示できる。
- 夜間や体調不良時に無理な外出を強制しない。
- 本人が再通知を選んだ場合は回数を制限しない。予定開始・制限開始の10分前から開始10分後まで、5分ごとに自動通知する。開始10分後に自動通知を止める。

### FR-10　段階的行動誘導

優先度：MVP必須
抽象的な活動を小さな行動へ分解し、順番に提示する。

<strong>例：</strong>
「数学を勉強する」
1. 椅子に座る。
2. 参考書を開く。
3. 前回の学習箇所を確認する。
4. 最初の問題に取り組む。

<strong>要求事項：</strong>
- タスクを複数のステップに分けられる。
- ステップごとに進捗を記録できる。
- タスクを途中終了できる。
- 活動誘導のみを一時停止できる。
- 誘導の一時停止によってSNSの厳格ロックを解除しない。

### FR-11　曜日別ルーティン管理

優先度：MVP必須
勉強、読書、運動、開発などを習慣として登録し、曜日ごとに予定を作成する。

<strong>要求事項：</strong>
- 習慣の作成・編集・削除。
- 実施曜日の設定。
- 開始・終了時刻の設定。
- 目標所要時間の設定。
- 最低達成時間の設定。
- 開始前通知の設定。
- 開始トリガーの設定。
- 毎週の繰り返し設定。
- 週間カレンダー表示。
- ルーティンの実行履歴保存。

同じ習慣を複数の曜日・時間帯に登録できる。日をまたぐルーティンは開始日の曜日に属する。複数のルーティンが重複した場合は後から登録したものを優先し、先に登録したものをサブルーティンとして扱う。3件以上重なってもすべて表示し、後から登録した順に優先度を示す。終了予定時刻を過ぎても未開始のサブルーティンには、責めない文言で警告を表示する。優先ルーティンの終了後、または優先ルーティンをスキップした場合にサブルーティンを表示する。サブルーティンの実行結果はサブルーティンとして記録する。優先ルーティンをスキップした場合はサブルーティンを先に表示し、休息または読書・瞑想などの低刺激タスクを次の選択肢として提示する。実行できなかったことを責めない。

### FR-12　ルーティンとSNSブロックの連携

優先度：MVP必須
ルーティン実行中にSNSの利用制限を適用できる。

<strong>要求事項：</strong>
- ルーティンにSNS制限の有効・無効を設定できる。
- SNS制限中でもルーティンを開始できる。
- 予定された習慣を行動誘発タスクより優先表示できる。
- ルーティン未達成に対する罰則を設けない。
- ルーティン終了だけを条件に厳格ロックを解除しない。

### FR-13　通知・行動誘導UI

優先度：MVP必須
通知を見逃しにくくし、次に行う行動を明確に提示する。

<strong>要求事項：</strong>
- デスクトップ通知。
- 通知音の設定。
- 前面表示による行動誘導。
- 予定開始・SNSのブロック開始の10分前から、開始10分後までの5分ごとの通知。
- 行動ステップの表示。
- 通知の一時停止。停止時間は15分以上で設定できる。一時停止中に別の予定が始まった場合、その予定の通知は止めない。一時停止が終了した予定は、開始10分後までの自動通知期間内なら5分間隔の通知を再開し、期間を過ぎていれば通知しない。
- 前面表示と、本人が選ぶ再通知の回数に設定上の上限は設けない。自動通知は予定開始・制限開始の10分前から開始10分後まで5分間隔とし、開始10分後に止める。
- 安全上必要な操作や通常業務を妨害しない表示方法。

### FR-14　活動記録

優先度：MVP必須
習慣や誘発された行動の実行結果を保存する。

<strong>記録項目：</strong>
- 対象習慣。
- 実行日時。
- 実行時間。
- 完了・一部実行・未実行。
- 行動開始に成功したか。
- 任意のメモ。

本人が実行できなかった理由を入力することは任意とする。

### FR-15　利用前後の状態記録

優先度：MVP必須
周期制限の利用可能時間が終了してBLOCKに切り替わるとき、SNS利用後のCBTを参考にした内省フォームを表示する。

<strong>記録項目：</strong>
- SNSを見終えたときの感情：ラジオボタンで一つ選択（必須）。
- 感情についての自由記述：任意、100文字程度。ただし感情で「その他」を選んだ場合は自由入力を必須とする。
- SNSを見たことによるメリット：自由記述、必須、100文字程度。
- SNSを見たことによるデメリット：自由記述、必須、100文字程度。

感情の選択とメリット・デメリットの両方を必須入力とし、未入力のままアプリ内でフォームを閉じられないようにする。保存後は本人が記録を開いて入力内容を編集できる。入力内容はローカルに保存し、記録日時から1か月が経過したものを古い順に自動削除する。Notion連携を設定した場合は指定ページにも自動記録する。記録画面の表示や入力状態は、SNSの遮断判定を変更しない。感情の選択肢は「満足」「落ち着き」「楽しさ」「疲れ」「不安」「後悔」「特になし」「その他：自由入力」とする。必須入力前にアプリが終了した場合は入力途中の内容を保存し、再起動時に未完了フォームを再表示する。未完了のまま次の利用周期が終了した場合も周期ごとに記録を残し、古いものから順に入力を促す。

### FR-16　行動転換の分析

優先度：後続機能
記録された行動データを分析し、活動転換に有効な条件を可視化する。

<strong>分析候補：</strong>
- SNS利用時間。
- 習慣実行率。
- 行動開始率。
- 外出後の活動復帰率。
- 時間帯別の活動成功率。
- 行動誘発タスク別の結果。

将来的には本人の実績に応じた行動推薦の最適化を検討する。

### FR-17　Notionへの内省記録

優先度：MVP必須（連携の利用は任意）
ユーザーがNotionの保存先ページURLを設定し、必要な接続認可とページへのアクセス権を付与した場合、保存済みの内省記録をそのページへ自動記録する。URLの入力だけでは書き込みを開始せず、接続状態と保存先ページへの書き込み可否を確認する。連携を設定していない場合、外部送信しない。Notionへの送信に失敗した場合も、ローカル記録は1か月経過後に予定どおり削除する。送信済みの内省記録をローカルで編集しても、Notion側の記録は更新しない。一時的な通信障害では1分、5分、15分、1時間後に再試行し、なお失敗する場合は「要対応」として本人が手動で再試行できるようにする。Notionが429・529を返した場合は`Retry-After`で指定された時間を優先する。記録ごとに固有IDと送信先IDを保存し、書き込み結果が不明な場合は送信先を確認してから再試行し、重複を防ぐ。状態は「送信待ち」「送信済み」「再試行中」「要対応」と表示する。認証・権限エラーは自動再試行せず「要対応」とする。

## 第4章　ユーザーフロー

### 4.1 SNSアクセス時

1. ユーザーが対象サービスにアクセスする。
2. OSレベルでアクセスを検知する。
3. 現在の制限ルールを評価する。
4. アクセス可能な場合、初回アクセスを起点にタイマーを開始する。
5. 利用可能時間を超えた場合、対象サービスを遮断する。
6. SNS利用後の感情とメリット・デメリットを記録する内省フォームを表示する。
7. 行動誘発エンジンが適切なタスクを提示する。
8. タスク実行結果を保存する。

### 4.2 週間ルーティン実行時

1. 設定された曜日・時刻が近づく。
2. 予告通知を表示する。
3. 開始トリガーを提示する。
4. ルーティン開始画面を表示する。
5. 実行中は必要に応じてSNS制限を適用する。
6. 目標時間の終了後、実行結果を記録する。

## 第6章　制御ルールと優先順位

### 6.1 SNSアクセス判定

アクセス許可・遮断は以下を踏まえて決定する。
1. OS側の安全・復旧要件。
2. 厳格ロックの有効性。
3. 時間帯制限。
4. ルーティン連動制限。
5. 周期制限。

複数の制限が有効な場合、原則として制限の厳しい判定を優先する。
一時解除による例外は設けない。

### 6.2 行動誘発の優先順位

1. 安全性・体調・必要な休息。
2. 実行中の習慣。
3. 開始予定の習慣。
4. SNSブロックに伴う行動誘発。
5. 空き時間に行う任意の活動。

### 6.3 時間管理

- 時刻はOSの時計とタイムゾーンを考慮して扱う。
- 再起動後に状態を復元する。
- 時計を手動変更した場合の不正な短縮を検知する。
- 利用可能時間・遮断時間・厳格ロックの経過時間には、PCのスリープ中の時間を含める。復帰時は実際の経過時間から状態を再計算する。
- 異常終了時は状態記録から再計算する。

### 6.4 緊急復旧

緊急復旧は、次の順序で実行できるようにする。通常ユーザーによる制限回避には使えず、管理者が実行した操作と結果を記録する。

1. 制御サービスの自動再起動を試みる。回復しなければ次の段階へ進む。
2. ネット接続不要の管理者認証付き専用復旧ツールで、ActShiftの制御を復旧または解除する。通常の設定画面や厳格ロックの編集操作とは分離する。
3. 専用ツールも使えない場合、OSの正規管理機構で、管理者がActShift専用のフィルターまたは拡張設定を停止・削除する。OS全体のネットワーク制御機能は停止しない。

各段階のOS別の実行可能性と手順は[通信遮断PoCのIssue #1](https://github.com/nto300002/ActShift/issues/1)で実機検証し、成功した手段だけを製品の復旧手順として確定する。

## 第7章　非機能要件

### NFR-01　セキュリティ

- 設定UIと制御サービスを分離する。
- 制御サービスには必要最小限の権限を与える。
- 権限のない設定変更を拒否する。
- 正規の復旧経路を維持する。
- 機密性の高い閲覧内容を不要に収集しない。

### NFR-02　信頼性

- UIの終了によって遮断機能が停止しない。
- 再起動後も設定を維持する。
- 設定の破損を検知する。
- ロック状態の不整合を検出・記録する。
- OSのネットワーク機能を恒久的に破壊しない。
- 制御機能の停止・異常終了時は、登録済み対象サービスの通信を遮断し、対象外と識別できた通信は許可する。対象かどうか識別できない通信は遮断し、管理者による復旧を待つ。制御サービスの自動再起動を試み、異常を記録・表示し、正規の管理者復旧経路を維持する。

### NFR-03　性能

- 常駐状態でのCPU・メモリ負荷を低く保つ。
- 通常のインターネット通信に不要な遅延を生じさせない。
- タスク通知とルーティン判定を安定して実行する。

具体的な性能上限値は技術検証時に設定する。

### NFR-04　プライバシー

- 個人用MVPではローカル保存を基本とする。内省記録は記録日時から1か月経過したものを古い順に自動削除する。
- クラウドアカウントを必須としない。
- Notion連携を本人が有効にした場合に限り、保存済みの内省記録を指定ページへ送信する。それ以外の行動履歴や習慣データは外部送信しない。
- 記録データの削除・エクスポートを可能にする。内省記録はアプリ内DBに保存し、記録ごとのファイルは自動生成しない。本人が必要時にCSVまたはJSON形式で手動書き出しできる。Notionへ送信済みの記録はNotion側の保存ポリシーに従う。

### NFR-05　ユーザビリティ

- 現在のロック状態を明確に表示する。
- 行動開始に必要な操作を少なくする。
- 通知音を設定できる。
- 未達成を責める表現を使わない。
- 行動誘発の介入強度を変更できる。

## 第11章　受入条件

### 11.1 遮断機能

- UIを終了しても遮断が継続する。
- PC再起動後にルールが復元される。
- 制御機能の異常時、登録済み対象サービスと対象か判別できない通信を遮断し、対象外と識別できた通信および正規の管理者復旧経路を維持できる（OS別の技術検証後に確定）。

- 利用可能時間N分を5〜30分、遮断時間M分を30〜500分に設定できる。

- 指定時刻に時間帯制限が開始・終了する。
- 時計変更・異常終了による不正な状態遷移を検知できる。

### 11.3 行動誘発

- 段階的にタスクを実行できる。
- 誘導を停止してもSNS制限が維持される。
- 予定開始・制限開始の10分前から開始10分後まで5分ごとに通知し、その後は自動通知を止める。
- 周期の利用可能時間終了時に内省フォームを表示し、感情の選択とメリット・デメリットの記述を必須として保存できる。必須項目を入力するまでアプリ内では閉じられず、保存後は編集できる。
- 内省記録は作成から1か月が経過すると古い順にローカルから削除され、Notion連携が有効なら指定ページへの自動記録を確認できる。

### 11.4 ルーティン

- 習慣を曜日・時間帯ごとに登録できる。

- ルーティン実行結果を記録できる。
- 複数の習慣を管理できる。
- ルーティンとSNS制限が独立して動作する。
- 優先ルーティンをスキップするとサブルーティンが低刺激タスクより先に表示される。

## 第12章　決定事項と詳細設計での確認事項

### U-01：ネイティブアプリの制限範囲【決定】

ネットワーク通信のみを遮断し、起動自体は禁止しない。

### U-02：周期の終了条件【決定】

毎朝10:00に、進行中のALLOW/BLOCKを含め周期をIDLEへ戻す。9:59から対象サイトを開いたまま、または対象ネイティブアプリを起動したままの場合も、10:00に新しいALLOWを開始する。対象を閉じている場合は、次の対象アクセスでALLOWを開始する。他の時間帯・ルーティン制限や厳格ロックは解除しない。10:00は通常編集の開始時刻でもあるが、周期リセットとは別のルールである。

### U-03：一時解除の適用範囲【決定・廃止】

一時解除機能を設けない。従来の適用範囲の検討は不要とする。

### U-04：待機完了時の挙動【決定・廃止】

一時解除機能を設けないため、解除待機と再確認は実装しない。

### U-05：タスク通知の強度【一部決定】

予定開始・制限開始の10分前から開始10分後まで5分ごとに自動通知し、開始10分後に止める。前面表示の頻度と、本人が選ぶ再通知の回数には上限を設けない。通知の一時停止時間は15分以上で設定可能とする。一時停止中に別の予定が始まっても、その予定の通知は止めない。一時停止の終了時点が対象予定の開始10分後までなら自動通知を再開し、その期間を過ぎていれば再通知しない。

### U-06：厳格ロックの期限と編集【決定】

厳格ロックの設定期間は30分以上。ロック中は、制限を厳しくする変更を含め通常の設定編集を一律に禁止する。ロック中以外も21:00〜翌10:00は通常編集と保存を禁止し、10:00〜21:00を編集可能時間とする。21:00時点の未保存変更は適用せず下書きとして保持し、翌10:00以降、厳格ロックが無効であれば保存できる。正規の管理者・緊急復旧経路は維持する。

### U-07：失敗時の通信制御【方針決定・技術検証待ち】

制御機能の停止・異常終了時は、登録済み対象サービスを遮断し、対象外と識別できた通信は許可する。対象かどうか識別できない通信は遮断し、管理者による復旧を待つ。制御サービスの自動再起動を試み、異常を記録・表示し、正規の管理者復旧経路を維持する。Windows・macOSでこの動作を保証できるか技術検証する。緊急復旧は第6章6.4の三段階を採用し、OS別の成立性を[Issue #1](https://github.com/nto300002/ActShift/issues/1)で確認する。

### U-08：予定の競合処理【方針決定】

重複時は後から登録したルーティンを優先し、先に登録したものをサブルーティンとする。優先ルーティンの終了後、またはスキップ時にサブルーティンを表示し、実行結果をサブルーティンとして記録する。優先ルーティンのスキップ時はサブルーティンを先に、休息・読書・瞑想などの低刺激タスクを次に提示する。3件以上の重複時もすべて表示し、後から登録した順に優先度を示す。終了予定時刻を過ぎても未開始のサブルーティンには、責めない文言で警告を表示する。実行できなくても罪悪感を強めない表現とする。

### U-09：習慣化の評価基準とSNS利用後の内省【方針決定】

SNSを見ていたはずの時間を本人がどう過ごせたかを重視する。ルーティン未達成でも、SNSを見ず穏やかに過ごせたことを肯定的な結果として扱う。周期の利用可能時間が終わった際には、SNS利用後の感情と、利用のメリット・デメリットを内省形式で記録する。単一の達成率で本人の価値を判定しない。

### U-09a：内省記録の保存とNotion連携【方針決定・詳細設計待ち】

感情の選択とメリット・デメリットの自由記述を必須とし、未入力では内省フォームをアプリ内で閉じられない。保存後は編集可能とする。内省記録は記録日時から1か月が経過したものを古い順にローカルから自動削除する。保存先のNotionページURLを設定し、接続認可とページへのアクセス権を付与した場合は、そのページにも自動記録する。Notionへの送信が失敗していても1か月後にローカル記録を削除する。感情の選択肢は「満足」「落ち着き」「楽しさ」「疲れ」「不安」「後悔」「特になし」「その他：自由入力」とし、「その他」選択時は自由入力を必須にする。必須入力前にアプリが終了した場合は入力途中の内容を保存し、再起動時に未完了フォームを再表示する。未完了フォームが複数ある場合は周期ごとに保持し、古い順に入力を促す。送信済み記録のローカル編集はNotion側に反映しない。Notion送信はFR-17の再試行・重複防止・状態表示に従う。内省記録はアプリ内DBに保存し、記録単位のファイルを自動生成しない。必要時にCSVまたはJSONで手動書き出しできる。

### U-09b：初期有効サービスと周期範囲【決定】

初期状態ではYouTube、Twitch、X、ユーザーローカル ライブランキング、好き嫌い.com、Yahoo!ファイナンスを制限対象として有効にする。周期の利用可能時間N分は5〜30分、遮断時間M分は30〜500分とする。

### U-10：スリープ中の経過時間【決定】

利用可能時間・遮断時間・厳格ロックの経過時間にPCのスリープ時間を含める。

### U-11：編集可能時間の境界【決定】

21:00に設定を編集中だった場合、未保存の変更は適用せず下書きとして保持する。翌10:00以降、厳格ロックが無効であれば保存できる。

## 第13章　成功指標

本アプリの成功を、SNSを何時間ブロックできたかだけでは判断しない。
最上位の成果指標は、<strong>「SNSを見ていたはずの時間を、本人が望む形で過ごせたか」</strong>とする。休息や穏やかな時間も肯定的な結果に含め、ルーティンの達成を必須としない。

<strong>主要指標：</strong>
- SNSの意図しない利用時間。
- 行動誘発後の着手率。
- 習慣の実行率。
- 習慣を開始するまでの時間。
- 行動転換の自己評価。
- SNS利用後の内省記録を本人が振り返れたか。

<strong>補助指標：</strong>
- ルーティンの継続率。
- タスク通知の無視率。
- SNS利用後に記録した感情の傾向。

これらを利用者の能力や価値の評価に使用せず、アプリの介入が有効かどうかの判断材料とする。

## 第14章　開発着手基準

本書の機能要件を実現するには、OSレベルの通信遮断と初回アクセス検知が最大の技術的課題となる。
本格的なUI実装より前に、Windows・macOSでそれぞれ以下を実証する。
1. ブラウザ拡張に依存しない対象サイト遮断。
2. 対象サービスへの初回アクセス検知。
3. ネイティブアプリの通信遮断。
4. ブロック中の既存通信への適用。
5. サービス終了・OS再起動時の制限維持。
6. 厳格ロックと安全な復旧の両立。

試作品の対象範囲、OS別の試験表、受け入れ条件、実測結果の提出方法は[通信遮断PoCのIssue #1](https://github.com/nto300002/ActShift/issues/1)に定義する。特に障害時の選択的遮断とオフライン管理者復旧は未実証であり、両OSで受け入れ条件を満たしたことを確認するまで実装方式を確定しない。

これらの技術検証と未確定事項の解消をもって、詳細設計および実装計画の確定へ進む。

## 最終定義

本アプリは、ユーザー自身が無益だと感じる行動を環境的に抑制し、その時間を本人が有益だと定義した行動に転換できるよう支援する、Windows・macOS対応の行動制御・習慣形成システムである。
SNSブロックは行動を止める手段、習慣管理は行動を継続する仕組み、行動誘発エンジンはその両者をつなぐ機能として位置づける。

## 要件定義の完成度と評価

今回の文書は、プロダクトの目的と主要な機能要件を統合した段階です。実装着手に必要な技術検証や詳細仕様は、まだ残っています。

| 領域 | 状態 |
| --- | --- |
| プロダクト思想・目的 | 確定 |
| 対象OS・利用者 | 確定 |
| SNS制限の基本仕様 | 確定 |
| 厳格ロック・一時解除なしの基本仕様 | 確定 |
| 行動誘発・曜日別ルーティン | 確定 |
| ルール競合時の優先順位 | 一部未確定 |
| Windows・macOSの遮断実装方式 | 技術検証待ち |
| 画面詳細設計・DB物理設計 | 未着手 |

特に重要なのは、ユーザーにとって有益な行動をアプリ側が勝手に決定しないことです。外出、読書、勉強だけでなく、本人が選んだ休息や趣味も有益な行動として扱える必要があります。
また、今後の要件検討では「ロック中に何を表示するか」だけでなく、「活動を始められなかった場合にアプリがどう振る舞うか」を明確にすると、過剰な行動管理を避けながら設計精度を高められます。
